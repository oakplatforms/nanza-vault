# 2026-09-25 · fab-new-cards-2026-09-22

**Input:** `migrations/import-csv/fab-new-cards-2026-09-22.csv` (711 rows, canonical migration
new-cards shape)
**Output:** `nanza-api/pricing/runs/2026-09-25-fab-new-cards-2026-09-22/all-priced.csv`
**Outcome:** 6/711 priced (4 medium, 2 low), 705 unresolved.

## Context

711-card drop spanning IAR (Usurp the Shadow Throne — a brand-new set released the same day as
this pricing run, 523 of 711 rows), PSM promos (72), three armory-exclusive decks (SVI 35 / SAT
32 / AMA 30), SPW (12), plus PEN/OMN/CRU singletons. Split into 15 shards of ≤50 rows, fanned out
in parallel on the haiku default, with a 48-row sonnet escalation planned for the flagged tail.

## What ran

- 15 `card-pricer` shards dispatched in parallel.
- **9 of 15 shards were rejected on the first pass for a false "oversized shard" reason** and had
  to be re-dispatched with a correction.
- **6 shard attempts (across shards 1/3/4/5/6/7) used the banned cardsrealm source** and had to be
  rejected and re-run a second (and in shard 6's case, third) time.
- Session-wide web-search budget (200/session) ran out partway through the corrective re-runs —
  affected 4 shard re-runs and the full escalation pass.
- 48-row sonnet escalation (highest-value unresolved tail: Marvel/Promo Marvel/Legendary/Fabled
  rows, plus the 2 `low`-confidence priced rows) could not execute at all — zero search budget
  remained by the time it launched.

## What the pipeline got wrong and how it was caught

**1. `wc -l` is not a valid row count on this pipeline's CSVs (new failure mode).** Nine of
fifteen first-pass workers rejected their assigned shard as "oversized" — reporting row counts of
130-254 against a 50-row cap — despite every shard being pre-verified with a real CSV parser
(`python3 csv.reader`) to be exactly ≤50 data rows. Root cause: this CSV's `effect`, `true_text`,
and `flavor_text` columns contain embedded newlines inside quoted multi-line fields (card rules
text spans multiple `<p>` paragraphs). A raw `wc -l` / naive line count treats every embedded
newline as a new row, wildly overcounting on a file that is otherwise perfectly valid CSV. Caught
because every rejection could be immediately falsified by re-parsing the same file with `csv`.
Fixed by re-dispatching with an explicit correction and the correct counting command. **This
produced a new standing lesson** (below) — the first CSV-mechanics failure mode this pipeline has
hit, as opposed to the research-quality failures every prior lesson addresses.

**2. cardsrealm used despite the existing ban (lesson 14 reinforced, not new).** Six shard
attempts across this run's corrective cycle used cardsrealm.com / fab.cardsrealm.com — already a
banned source per standing lesson 14 from an earlier run. Two sub-patterns:
- Shard 7's first attempt built a **set-level bulk estimate** for ordinary IAR commons/rares
  ("$0.40-$0.56 for commons") sourced from cardsrealm's set-summary averaging — simultaneously a
  lesson-14 violation and a rule-17/lesson-6 violation (IAR is an ordinary newly-released set, not
  the narrow armory-exclusive bulk exception).
- Shards 3, 4, 5, 6 used cardsrealm as a convenient per-card lookup for 5-25 rows each, at
  `medium`/`low` confidence, treating an explicitly banned aggregator as a legitimate source.
- Shard 3 additionally shipped 16 PSM promo rows with no named source at all ("thin presale
  data") — a bare guess wearing a confidence label.
All six were caught by grepping every shard's pricing-report for "cardsrealm" after the fact,
rejected (files renamed `*.REJECTED-*.csv`, excluded from the merge), and re-dispatched with an
explicit source ban repeated in the prompt. Every re-run came back honestly blank or near-blank,
matching the three shards (8, 10, 12) that got it right on the first try. **Note on precedent:**
an earlier run (2026-08-21-fab-new-cards-part6) had found cardsrealm's *per-card dated
price-history tables* (distinct from the set-summary page) usable when they carried explicit USD
labels — this run did not re-litigate that nuance; the current methodology text bans cardsrealm
outright, workers were instructed accordingly, and that's what was enforced here. Worth a look
if a future run wants to revisit whether the ban is broader than it needs to be.

**3. Session search-budget exhaustion mid-correction.** Re-running 9 shards plus a 48-row
escalation on top of the original 15-shard fan-out pushed past the session's 200-search cap.
Four shard re-runs and the entire escalation pass hit zero remaining searches. In every case the
worker **refused to fabricate a result** — no reused stale evidence, no memory-based guess dressed
up as research. Shards 3/5/6/7 finalized honestly with whatever evidence they'd gathered before
hitting the wall (all came back correctly blank/near-blank). The escalation agent went further:
it attempted a `WebFetch` fallback against TCGplayer/SCG/FabFoundry/Card Kingdom, found nothing
usable (JS shells, DNS failure, no matching cards), and **stopped and reported the blocker
instead of writing 48 rows that would have looked like genuine thin-data findings but were
actually a budget outage**. This is exactly the honest failure mode the pipeline wants when it
hits a hard resource wall — no rule change needed, but it's a real operational constraint worth
flagging: a 711-card run with any amount of rework can outrun one session's search budget.

## What changed as a result

**New standing lesson added:** row counts on this pipeline's CSVs must come from a real CSV
parser, never `wc -l` or a raw line count — `effect`/`true_text`/`flavor_text` contain embedded
newlines inside quoted fields that inflate naive counts by 2-5x. Added to the methodology's
"Pricing methodology" section and to the INDEX's standing lessons list below.

No change to the cardsrealm ban (lesson 14) — this run reinforces it through repeated real
violations rather than exposing a gap in the rule itself. Flagged as a note for a future run to
possibly revisit the earlier per-card-history-table nuance, but not touched here.

No change needed for the search-budget behavior — the failure mode observed (correctly refusing
to fabricate, reporting the blocker) is the desired behavior, not a bug. Documented as an
operational scaling constraint for large runs, not a methodology fix.
