# Sources & Insights — Fable Design Review (2026-07-05)

Reviewed: `nanza-vault/nanza-api/solution-designs/sources-and-insights.md` (canonical) +
`nanza-vault/nanza-admin/solution-designs/sources-and-insights.md` (admin surface), against
nanza-api, nanza-admin, nanza-mobile, and the existing implementation in **oak-cortex**.

## Verdict

**The design is sound. Green light after the doc gaps below are closed.** The core shape —
one `Source` + one `Insight` typed by a shared `SourceType` enum, deterministic rollup as
default with AI escalation, per-product batched loops — holds up against all three codebases
and against the real oak-cortex system. None of the findings are structural; they are missing
sections and undecided details that agents *will* guess wrong if left open.

Confidence: 0.9 overall on the architecture; the items below are where confidence drops.

## 1. Critical gaps in the design doc (fix before building)

### 1.1 The Snapshot model is missing from the data model ⟵ biggest gap
Build-order step 3 says "snapshot store + deterministic rollup," but the Data Model section
defines only `Source` and `Insight`. The rollup cannot run without the 14-day history table.
oak-cortex has `price_snapshots` (`supabase/migrations/006_entity_schema.sql:41-49` +
`020_product_price_and_ignored.sql:14-15`): `entity_id, source_id, price numeric(10,2),
currency, condition, snapshot_at, ignored, ignored_reason` — append-only, one row per
(entity, source, day). The design needs a Prisma equivalent, e.g.:

```prisma
model SourceSnapshot {
  id            String    @id @default(cuid())
  price         Decimal?  @db.Decimal(10, 2)   // or a json `value` if generalizing beyond pricing
  currency      String?
  condition     String?
  ignored       Boolean   @default(false)
  ignoredReason String?
  sourceId      String
  productId     String    // (or entityId — see 2.3)
  createdAt     DateTime  @default(now())
  @@index([productId, createdAt])
  @@index([sourceId])
}
```
Decide too whether snapshots generalize (a `value Json` for future EVENT/ARTICLE candidates)
or stay pricing-specific with non-pricing candidates held only in loop memory. Recommendation:
pricing-specific now, rename-safe (`SourceSnapshot`, not `PriceSnapshot`) — candidates for
articles don't need 14-day history the way prices do. Confidence 0.85.

### 1.2 `Source` is missing the noisy/tolerance fields the prose promises
The doc says the hardcoded bands and "which source is noisy" flag "become fields on the
Source model (see below)" — but the field table only lists `weight`. In oak-cortex these are
hardcoded per-domain (`calculate-product-prices.ts:41-49`: participating source IDs + `noisy`
flag; bands at lines 63-64). Add explicit fields — `isNoisy Boolean @default(false)` (or
`toleranceLow`/`toleranceHigh` floats) — rather than letting them sink into the untyped
`config` json. Confidence 0.9 that explicit fields beat json config: the rollup branches on
them, and admins should see/edit them as first-class fields.

### 1.3 Insight supersession & retention is unstated
"Pricing insights supersede prior ones" has no mechanism. With continuous loops over the
catalog, PRICING `Insight` rows accumulate one per product per rollup — unbounded. State:
- current = latest `createdAt` per (product, type), **or** an `isCurrent` flag maintained on write;
- a retention rule (e.g. keep last N pricing insights per product, prune the rest);
- a cap for non-pricing types (e.g. max K ARTICLE insights per product, orchestration replaces).

### 1.4 How the local-Claude loop writes back — no auth story
The loop runs on a local machine but must write snapshots, `Product.price`, and `Insight`
rows. nanza-api's write path is Cognito-gated: the API Gateway authorizer derives role from
`cognito:groups` (`lambdas/authorizerHandler.ts:210-223`), and admin writes use
`validateAdmin(reqUser, adminId)` which requires the body's `adminId` to belong to the caller
(`src/validation/user.ts:21-71`). Two viable paths:
1. **Machine admin (recommended, 0.8)** — a dedicated bot user in the admin Cognito pool +
   an `Admin` row; the loop authenticates like nanza-admin does and stamps its own
   `createdById`. Keeps every write inside the API's validation/audit path, works from any
   machine, and the Insights provenance shows "pricing-bot".
2. Direct Prisma/DB access from the loop (what oak-cortex does with Supabase) — fewer moving
   parts but bypasses validation/audit and couples the loop to the schema. Rejected as the
   default; acceptable escape hatch for bulk snapshot inserts if endpoint throughput hurts.

### 1.5 Where the deterministic rollup runs — split it from fetching
The doc puts everything in the local loop. If the machine is off, prices stale *and* the
"deterministic fallback" isn't running either — the fallback needs a home that's always on.
nanza-api already has the exact pattern: scheduled Lambdas (`cancelOrder`/`reviewOrder`,
`serverless.yml:245-263`, `reviewOrderHandler.ts` init pattern). Recommendation (0.85):
- **Local Claude**: fetching (scrape/API per source) + the AI orchestration escalation.
- **Scheduled Lambda (daily cron)**: the deterministic rollup — reads snapshots, writes
  `Product.price` + the PRICING insight, flags ambiguous cases for the AI to revisit.
This makes the proven cheap path serverless and reliable; the AI layer becomes purely
additive. Alternative (all-local, as written): simpler, but a laptop outage silently freezes
the whole pricing system. Rejected for the fallback path specifically.

## 2. Codebase realities the design should absorb

### 2.1 `Product.price` AND `Product.pricingStatus` already exist
`schema.prisma:958-959` — `price Decimal? @db.Decimal(10,2)` and
`pricingStatus ProcessStatus?`, with `pricingStatus` already globally omitted from API
responses (`prismaHelpers.ts:80-82`). The rollup has a ready-made landing spot and an
internal status field. The design should name `pricingStatus` as the loop's per-product state
(PENDING/COMPLETED/FAILED) instead of inventing one.

### 2.2 `EntityType.EVENT` already exists — different axis than `SourceType.EVENT`
`EntityType` = PRODUCT/SERVICE/CONTENT/EVENT (`schema.prisma:16`). No conflict technically,
but agents grepping for `EVENT` will find both; the design doc should include one line
distinguishing them (catalog-item kind vs intelligence kind).

### 2.3 Pick ONE relation for Insight — recommend Entity
The doc says `product / entity` relation. They're 1:1 (`Product.entityId @unique`) so either
works, but pick one. **Recommend `entityId` (0.75)**: listings, bids, and entityTags all hang
off Entity; mobile's detail fetch is `GET /entity/{id}?include=...` and `generateIncludes`
would serve `include=insights` for free; brand scope lives on Entity (`Product` has no
`brandId`). Alternative (product): semantically "product intelligence," but forces
`include=product.insights` and a join for brand-filtering. Snapshots should follow the same
choice.

### 2.4 Brand-scoped sources: per-brand rows, and that's fine
oak-cortex already models "eBay for OPTCG" and "eBay for FaB" as *separate source rows* with
different IDs, weights, and noisy flags. The design's single `brand` relation matches that
reality — keep it required and create per-brand rows (allows per-brand weight/noisy tuning).
Just note that when seeding from oak-cortex, **eBay's weight is an implicit 0.8 default**
(never explicitly stored) — set all weights explicitly on migration: TCGplayer 0.95,
PriceCharting 0.90, Zulus 0.85, eBay 0.8, FaB Stocks market 0.85 / avg 0.70.

### 2.5 Prisma conventions the models must follow (agents will need these)
- Enums in the top block (`schema.prisma:16-237`), models below; **no inline comments** in
  schema (user preference); enums/models in their separate sections.
- `String @id @default(cuid())`, `createdAt/updatedAt`, money = `Decimal @db.Decimal(10,2)`.
- Audit fields require **back-relations on `Admin`** (`schema.prisma:271-288`):
  `createdSources Source[] @relation("CreatedBy")` etc. — the Admin model must be edited too.
- `@@index([brandId])` on Source (mirrors Set/Entity/BrandTag); brand-scoping on list
  endpoints is the `AND[]`-append idiom (`src/routers/entity.ts:116-160`).
- New router: `src/routers/source.ts` → registered in `all_routes.ts` **before**
  `universalRouter` (must stay last). Copy `src/routers/brand.ts` wholesale for the
  admin-gated CRUD pattern; plural-list/singular-item URLs (`/sources`, `/source/:id`);
  GET/POST/PUT/DELETE only; `paginatePrisma` + `generateIncludes` on lists.
- New models flow into `@oakplatforms/types` automatically via the prisma-json-schema →
  openapi-typescript pipeline; needs a version bump + publish (admin is on 0.1.61).
- User runs all migrations manually — agents generate, never run, `prisma migrate`.

### 2.6 Admin surface: two concrete decisions the doc leaves open
- **Insights panel location.** Products has *no* detail panel today — only the
  `CreateOrEditProduct` edit dialog (a stack of card sections) and a commented-out preview
  column. Closest precedent for a read view is Orders' `OrderDetailModal`. Recommend (0.7):
  a read-only "Insights" card section appended inside `CreateOrEditProduct.tsx` for v1 —
  smallest delta, matches the existing card-stack idiom. Alternative: a new
  `ProductDetailModal` à la Orders — better long-term home once ARTICLE/EVENT insights
  arrive, but a bigger build; defer it.
- **Weight control.** No slider primitive exists anywhere in nanza-admin. Use the established
  `Input type="number" step="0.01"` (e.g. `CreateOrEditProduct.tsx:304`) with 0–1 min/max,
  not a net-new slider component. Update the admin doc's "slider" wording.
- Everything else in the admin doc checks out: `src/app/Sources/` + `data/` hooks + a
  `sourceService`, the triplicated nav (TopNavbar array, Sidebar inline links, AppLayout
  routes — all three must be edited), `?create=true` deep-link pattern, `useSession()` →
  `createdById`/`lastModifiedById` stamping. The Orders page has the exact enum
  status-filter pattern to copy for the type filter (`Orders/index.tsx:154-168`).

### 2.7 Mobile: explicitly out of scope for the PRICING build — say so
There is no mobile design doc and no insights surface in the app. Crucially, **pricing needs
zero mobile changes**: Fair Market already renders `entity.product.price` (EntityModal
price row, `EntityCard/List.tsx`), and scalar updates flow through with no client work. A
future insights UI is net-new (an EntityModal section + `include=insights` in
`fetchEntityDetail.ts` + types bump). Recommend the canonical doc state: *mobile is a
consumer of `Product.price` only in phase 1; insights UI on mobile is a later phase with its
own design.* This prevents an agent from inventing mobile work.

## 3. Algorithm port — verified against oak-cortex, with 3 port notes

The doc's 9-step description is **faithful** to `oak-cortex/scripts/calculate-product-prices.ts`
(constants at lines 51-69, pipeline at 144-268). Port from that file as the reference
implementation, not from the doc prose. Notes:
1. **No-history branch:** when historical median is null/≤0, all today-prices pass the band
   check and only the cross-source steps apply (lines 190-193). The doc glosses this; the
   port must keep it.
2. **Actual step order:** tolerance → floor → cross-source tighten → noisy corroboration →
   weighted avg. Same ops as the doc, slightly renumbered — follow the code.
3. **Stale comment trap:** migration `020`'s comments say "× 1.08"; the real factor is
   `PRICE_FACTOR = 0.945` applied per-term (mathematically same as once on the average).
   Trust the code constant. Consider making 0.945 a config value rather than a new hardcode.

Scale sanity: oak-cortex runs ~5k entities/source in ~3.5h with 1 worker, 4 sources in
parallel, daily cron, snapshots batch-inserted 100 at a time, rollup at 10 async workers with
`--since-hours 24` to only recompute freshly-snapshotted products. The design's "~100k
products" is ~20× today's scale — the stalest-first continuous pacing in the doc is the right
answer, but the doc should inherit `--since-hours`-style "only roll up what changed" from
oak-cortex.

## 3.5 oak-cortex is being deprecated — cutover plan needed (user note, 2026-07-05)

The design should treat oak-cortex as **read-once reference, then gone** — no runtime
dependency on it, ever. Three consequences the doc doesn't cover yet:

1. **Seed migration.** One-time export from oak-cortex into the new models: `sources` table
   (+ explicit weights per §2.4, + the per-domain noisy flags from
   `calculate-product-prices.ts:41-49`) → `Source` rows; `entity_source_urls` → into
   `Source.config`/per-product fetch specs, or a follow-on model if per-product URLs are kept.
2. **History backfill.** Without it, every product cold-starts in the "no history" branch for
   14 days and the rollup runs band-check-blind. Backfill the last 14+ days of
   `price_snapshots` into `SourceSnapshot` at cutover (entity IDs will need mapping between
   the two catalogs — verify oak-cortex `entities` ↔ nanza `Entity` correspondence before
   assuming this is mechanical).
3. **Cutover sequencing.** Keep oak-cortex's daily run alive until the nanza loop + rollup
   are live and verified against it (run both for a few days, diff the computed prices),
   then decommission. Decommission = stop the cron + archive the repo; the design doc's
   "how price is calculated today" section becomes the historical record.
