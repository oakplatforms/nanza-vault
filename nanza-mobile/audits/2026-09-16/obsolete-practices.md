## 4. Tooling hygiene

**(a) Broken tsconfig extends.**
`tsconfig.json:2` — `"extends": "@react-native/typescript-config/tsconfig.json"` resolves to `error TS6053: File '@react-native/typescript-config/tsconfig.json' not found.` even though `ls node_modules/@react-native/typescript-config` shows the package **is** installed (`README.md`, `package.json`, `tsconfig.json`, `tsconfig.strict.json` are all present) and its `package.json` declares a proper `exports` map (`"." : "./tsconfig.json"`). `npx tsc --showConfig` reproduces the same TS6053 and refuses to print a resolved config at all — meaning tsc cannot resolve the `exports`-based subpath from tsconfig's `extends`, most likely a TS-version/resolution-mode mismatch (worth checking that the installed `typescript` 5.9.3 and the CLI actually agree on `moduleResolution`/`extends` package-exports resolution; this is a known rough edge). Net effect: none of the base preset's `strict: true` (redundant since local file also sets it), `allowImportingTsExtensions: true`, `allowArbitraryExtensions`, or its curated `lib` list are actually being applied — the project is relying entirely on its own local `compilerOptions`.
  - `allowImportingTsExtensions` is **only** declared in the unreachable base config (`grep -rn "allowImportingTsExtensions" tsconfig.json node_modules/@react-native/typescript-config/` finds it solely in the base file) — this directly explains the 26 TS5097 errors ("An import path can only end with a '.ts'/'.tsx' extension when 'allowImportingTsExtensions' is enabled"), all in files that import with explicit extensions.

**(c) Two lockfiles.**
`package-lock.json` (534,778 bytes) and `yarn.lock` (298,490 bytes), both last modified `Sep 14 14:52` (same mtime — likely both regenerated by whichever install command ran last) and **both are git-tracked** (`git ls-files package-lock.json yarn.lock` returns both). `README.md` documents both `npm` and `yarn` command variants side-by-side (e.g. lines 42-45, 56-59, 66-69: "using npm" / "OR using Yarn") without picking one, and there's no CI config anywhere in the repo to check which one a pipeline actually installs from. Recommendation: pick one (the `scripts` block and `.nvmrc`/engines convention lean npm — no yarn-specific scripts exist) and delete the other lockfile + trim the README's parallel instructions.

**(d) Node version / polyfill.**
  - `.nvmrc` pins `21.7.1` — Node 21 was never an LTS line and reached end-of-life in June 2024; it's fully unsupported today.
  - `package.json` `engines.node` only requires `>=20`, which is looser than `.nvmrc` and doesn't prevent installing on an EOL Node 21 or on Node 24/25 with potentially different behavior.
  - `polyfill.js` patches `Array.prototype.toSorted/toReversed/toSpliced/with` "for Node.js 20+ compatibility" and is force-loaded via `NODE_OPTIONS="--require $(pwd)/polyfill.js"` in **every** `npm run` script that touches Metro/CLI (`android`, `ios`, `start`) plus a standalone `scripts/node_with_polyfills.sh` wrapper. Verified directly: on this machine's Node v22.21.0, `typeof [].toSorted` is `"function"` natively — these methods shipped in V8 as of Node 20.0.0 (announced originally for ES2023). The polyfill (and its `NODE_OPTIONS` wiring in 3 npm scripts + a dedicated shell script) is dead weight for any Node ≥20 environment, which is already the documented minimum (`engines.node: >=20`). It was presumably needed for some Node <20 CLI dependency at some point; nothing here still needs it.

**(e) Babel / env handling.**
  - `@babel/plugin-transform-private-methods` with `{ loose: true }` is still explicitly added in `babel.config.js`. `@react-native/babel-preset` (which RN 0.83 ships) already includes modern class-features transforms; this plugin is likely a holdover from an older preset version that didn't bundle it, or from a loose-mode requirement elsewhere in the transform chain (loose mode across plugins must stay consistent to avoid runtime mismatches) — worth confirming empirically (remove and rebuild) rather than asserting it's dead, since "loose" private-method transforms can silently change class-field semantics if only partially applied.
  - `react-native-dotenv` (babel-time `.env` → `@env` module) is the env mechanism in use (`babel.config.js` plugin config), not `react-native-config` (native-level env injection) — the app has standardized on one approach, not a mixed legacy/current pair; no obsolescence issue, just noting which was chosen.
  - `.env` is correctly gitignored (`.gitignore:66` `.env`) and confirmed **not** tracked (`git ls-files .env` returns nothing).

**(f) `types: ["jest"]` with no Jest installed.**
`tsconfig.json`'s `types` array includes `"jest"`, but `node_modules/@types/jest` does not exist, and there are zero `*.test.ts`/`*.spec.ts` files anywhere under `src` (`find src -iname "*.test.ts*" -o -iname "*.spec.ts*" | wc -l` → 0). This matches CLAUDE.md's explicit "we are not writing automated tests" directive — but the `types: ["jest"]` entry is a leftover reference to global Jest types that aren't installed, which is harmless today only because nothing in the codebase actually calls a Jest global; it should be removed to match the no-tests policy and avoid a future `Cannot find type definition file for 'jest'` error if `skipLibCheck`/resolution behavior changes.

## 6. Code-practice smells

- **`console.log`**: 0 occurrences anywhere in `src` — clean; no need for a babel strip-console plugin since there's nothing to strip.
- **`setTimeout`**: 55 occurrences across `src` — a mix of debounce/animation-sequencing and what are likely synchronization hacks (e.g. "wait N ms for the native side to settle"); not individually triaged here, but the count is high enough to warrant a follow-up pass distinguishing legitimate debounce timers from ad hoc race-condition workarounds.
- **String-typed navigation params**: `navigation.navigate('ScreenName', ...)` with a string literal first argument appears 99 times. Combined with the 34 untyped `useNavigation()` calls (section 3), this is the dominant pattern — route params are largely stringly-typed rather than flowing through react-navigation's generic param-list typing, which is a real but large-surface cleanup (touches call sites app-wide), not a quick fix.
- **`as unknown as`**: 22 occurrences — a double-cast escape hatch that bypasses type safety; each is worth a targeted look since this repo's CLAUDE.md explicitly bans `any` (rule 10) and `as unknown as` is a common way to functionally reintroduce `any` without the linter catching it (the `no-explicit-any` rule doesn't flag `as unknown as X`).
- **Non-null assertions (`!.`)**: only 8 occurrences by the pattern used — low density, not a systemic issue.
- **Duplicated utility functions**: `formatPrice`/equivalent is implemented independently in at least 3 places — the canonical `src/utils/formatPriceAsDollar.ts` (`formatPriceAsDollar`), plus local re-implementations in `src/screens/trade/TradeScreen/CollectTab.tsx:76` (`formatPrice`) and `src/components/global/Badge/Price.tsx:13` (`formatPrice`). `clamp` logic is inlined ad hoc in at least 6 places (`CollectScanItemsScreen`, `CollectTab`, `entrance.tsx`, `PostComposer.tsx` (as `clampToTextLimit`), `ZoomableImage` ×2) with no shared `clamp` utility despite the repeated `Math.max(min, Math.min(max, value))` shape. `formatDate` has one local implementation (`PayoutHistoryScreen/index.tsx:36`) with no canonical utils-level counterpart found — worth checking if a shared date formatter should exist. `truncate` has zero implementations found (not a duplication issue, just absent).
- **i18n scope** (correction to the audit brief's premise): **`src/lang/` is not empty** — it contains `en.json` (8,347 bytes), `fr.json` (8,497 bytes), `ja.json` (9,545 bytes), and `i18n.js`, all modified `Sep 11` (recent, active). 9 files actively import `useTranslation`/`react-i18next`. However, the ratio is stark: **1,007 `<Text` elements in `src/tsx` files vs. only 9 files using translation** — i18n is real infrastructure that's only lit up in the auth flow and a couple of card/profile components, while the other ~99% of user-facing text is hardcoded English strings. This isn't dead weight (it's wired up and working), but it is very partially adopted — worth deciding explicitly whether the intent is "localize everything eventually" (in which case the other 1000+ Text nodes are a known backlog) or "auth-only localization is intentional" (in which case the `i18next`/`react-i18next` dependencies are justified as-is either way).
- **Magic numbers outside `src/constants.ts`**: `src/constants.ts` exists and is used, but a targeted grep for 3+-digit `setTimeout` delays outside that file still finds 10 call sites with inline numeric literals (e.g. `setTimeout(fn, 300)`-shaped calls) rather than named constants — a minor consistency gap against the file's own stated purpose.
